# FINTALLY — Code of Conduct

**Copyright © 2026 Anshu Gondi**

FINTALLY is an open-source project built around privacy, user sovereignty, transparency, systems engineering, and open collaboration.

This Code of Conduct exists to make the project a respectful, technically rigorous, and welcoming environment for everyone who contributes to or participates in the FINTALLY community.

---

## 1. Our Community

We welcome contributions from people with different levels of experience and from different technical backgrounds.

You may contribute through:

* Source code
* Bug reports
* Feature requests
* Security research
* Performance analysis
* Benchmarks
* Documentation
* Testing
* UI/UX
* Architecture proposals
* Code review
* Technical discussions
* Community support

All legitimate contributions are valuable when they are made constructively and in good faith.

---

## 2. Expected Behavior

Community members are expected to:

* Treat others with respect
* Communicate professionally
* Assume good faith unless there is clear evidence otherwise
* Give constructive technical feedback
* Explain disagreements using technical reasoning and evidence
* Respect different levels of experience
* Welcome questions from newcomers
* Credit other contributors for their work
* Respect project maintainers and contributors
* Keep discussions focused on improving the project
* Protect private and sensitive information
* Follow the project's security-reporting procedures
* Respect the project's license and intellectual-property requirements

Technical disagreement is completely acceptable.

Personal attacks are not.

---

## 3. Technical Standards

FINTALLY is a systems-oriented project.

Technical discussions should, where appropriate, focus on measurable and reproducible evidence.

For performance-sensitive changes, contributors are encouraged to provide:

* Benchmarks
* Profiling information
* Memory measurements
* CPU measurements
* Latency measurements
* Relevant hardware information
* Reproduction steps

Statements such as "this is faster" should preferably be supported by measurements.

The project values engineering correctness over arguments based solely on preference.

---

## 4. Architecture and Design Discussions

FINTALLY intentionally has a defined architectural direction:

* React.js is the primary frontend technology.
* Rust is the primary backend orchestration layer.
* C, C++, and other systems languages may provide specialized native engines and extensions.
* Components should be designed for low memory consumption.
* Performance-sensitive paths should target low latency.
* Privacy should be preserved through architecture rather than relying solely on policy.
* Unnecessary services, dependencies, allocations, and data movement should be avoided.

Contributors are free to challenge architectural decisions.

However, architectural proposals should explain:

* The problem being solved
* The proposed design
* Alternatives considered
* Performance implications
* Memory implications
* Security implications
* Maintenance implications
* Compatibility implications

Disagreement is welcome when it improves the engineering quality of the project.

---

## 5. Unacceptable Behavior

The following behavior is not acceptable:

* Harassment
* Discrimination
* Threats
* Personal attacks
* Deliberate intimidation
* Trolling intended to disrupt the project
* Repeated bad-faith arguments
* Doxxing or exposing private information
* Publishing another person's private information without permission
* Sexual harassment
* Hate speech
* Deliberate impersonation
* Malicious disruption of project infrastructure
* Deliberate introduction of hidden telemetry or data collection
* Deliberate introduction of security vulnerabilities
* Misuse of security research to harm users
* Circumventing project security controls for malicious purposes
* Deliberately submitting plagiarized or improperly licensed code

Technical criticism is not harassment.

Strong disagreement about code, architecture, algorithms, performance, or implementation is permitted when communicated professionally.

---

## 6. Privacy and User Data

FINTALLY deals with potentially sensitive financial information.

Community members must never intentionally publish or expose another person's:

* Financial records
* Account information
* Authentication credentials
* API keys
* Private configuration
* Personal identifiers
* Private communications
* Local database contents
* Assistant context
* Other sensitive information

When creating bug reports or reproductions, contributors should remove sensitive information before publishing it.

---

## 7. Security Research

Security research is welcome and encouraged.

Researchers should follow responsible disclosure practices and should avoid unnecessarily exposing users to an actively exploitable vulnerability.

Security vulnerabilities should be reported through the process described in `SECURITY.md`.

Do not use public issue trackers to disclose sensitive vulnerability details unless the vulnerability has already been appropriately coordinated for public disclosure.

---

## 8. Code Review

Code review should focus on the implementation rather than the person who wrote it.

Reviewers should consider:

* Correctness
* Security
* Performance
* Memory usage
* Maintainability
* API design
* Error handling
* Testing
* Concurrency
* Resource management
* Privacy implications
* Architectural consistency

Review comments should explain the technical reason for requested changes whenever practical.

---

## 9. Maintainer Responsibilities

Project maintainers are responsible for helping maintain a healthy technical and community environment.

Maintainers may:

* Request changes
* Reject technically unsuitable contributions
* Close discussions that become disruptive
* Moderate inappropriate behavior
* Temporarily restrict participation
* Remove contributions that violate project policies
* Take other reasonable actions necessary to protect the project and its community

Maintainer decisions should be made in good faith and with the project's technical and community interests in mind.

---

## 10. Enforcement

Instances of unacceptable behavior may be reported to the project maintainers through the project's designated communication channels.

Reports should include enough information to understand:

* What happened
* When it happened
* Where it happened
* Relevant links or evidence
* Any immediate security or privacy concerns

Reports will be reviewed as appropriate.

The project may take action proportionate to the circumstances.

---

## 11. Scope

This Code of Conduct applies to:

* Project repositories
* Issue trackers
* Pull requests
* Discussions
* Project documentation
* Official project communication channels
* Project-managed community spaces
* Other spaces where an individual is representing FINTALLY

---

## 12. Good-Faith Participation

FINTALLY is an engineering project.

Mistakes are expected.

A contributor who introduces a bug, misunderstands an architectural decision, submits an inefficient implementation, or makes an incorrect technical assumption should be given an opportunity to correct it when acting in good faith.

The objective is to improve the software, not to punish people for learning.

---

## 13. Final Principle

The FINTALLY community should operate according to a simple principle:

> **Challenge ideas rigorously. Respect people completely.**

Build better software through evidence, experimentation, transparency, and collaboration.
